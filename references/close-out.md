# Close-out — required when a document's coding completes

A document is not finished when its last quotation is written; it is finished when the study's companion documents reflect it and the project is backed up. The close-out below is part of the job, not an offer — produce it unprompted, in this order, before treating the document as done. Skipping it silently loses exactly the knowledge (scope rulings, uncoded beats, cross-case flags) that the next session will need and cannot reconstruct.

You are reading this file at close-out time on purpose: in a long session the start-of-session read has usually been cleared from context, and a close-out done from memory compresses "update the study's two documents in place" into "deliver some notes." That has happened. Work from this file, not from memory of it. Then, as the first action, copy and unpack the two original companion documents (the case-status file and the coding brief, unzipped if they are .docx) so that the deliverables are those documents by construction and not fresh files that resemble them.

**Where the documents live decides how they are delivered.** If the study's documents are files on the researcher's machine that you can reach (for example in Claude Code), edit them there and save each updated document as the next version beside the original — same name, version number raised — never over the original. If they were attached to a chat, deliver the edited documents as files for the researcher to download. Either way the deliverable is the study's own document, edited in place.

0. **Verify first.** Pull the full list_quotations for the document, save it, and compare it against your on-disk log (`session_log.py compare`): same spans, same codes, every quotation commented. The counts in the summary and the files come from the live list, not from memory.
1. **The contrary-reading pass.** From the saved document text and the live quotation list, compute every stretch that carries no quotation (`uncoded.py`). Read each one once more against the study's frame, deliberately looking for the reading you did not take the first time — the beat the frame would care about, the code the noun search would have found. Bring back what you find as ordinary items (suggestion, skip, or anchor), one per turn, logged with `--pass contrary`; report "nothing found" as plainly as a find. This pass exists because the uncoded remainder is where an assistant's first reading hides its bias.
2. **A compact summary** of what was decided: codes applied (yours and theirs), splits and nests chosen, scope rulings made along the way, optionals declined, where the researcher overruled you and how. Close it with the same fixed figures every time, taken from the live list and the log (`figures.py`), so sessions can be compared and reported in a methods section: quotations written; code applications; codes used; NEW codes proposed, created, declined; uncoded anchors; items recommended as skip and the skip ratio (skips / all items presented); the confidence distribution of items presented (strong / arguable / stretch) and of items accepted; how often the researcher modified or overruled a recommendation; uncoded stretches examined in the contrary-reading pass and what came of them; process lapses. Keep it short — this is a record, not an essay.
3. **The updated case-status file, delivered as a file.** Not a row pasted in chat: draft the complete updated document — the interviewee's row in the progress table, a full detail section (background, session verification record, coverage, the session figures, codebook changes, scope decisions made on this document, observations feeding cross-case patterns, the deliberately-uncoded beats with offsets and reasons, reference codes, a full quotation table), any flag counts re-examined and cross-references added — in the study file's own format. Produce it by editing the study's own document in place (inserting into the original file with its styles, tables and headings intact) rather than rewriting it, so that everything the researcher did not ask you to touch is unchanged. Deliver it so the researcher can review it and replace their copy. Every fully coded document produces this file, without exception, and it is always the study's own file edited in place — never a Markdown or plain-text rendering of its content, even as an interim step, because a rendering is what gets delivered when the real edit is skipped.
4. **The brief check, with an explicit verdict.** Re-read the session for anything codebook-level: scope rulings, definitional boundaries preserved or extended, declined NEW-code proposals worth recording, method lessons, tool behaviour discovered, and any study frame elicited at session start that the brief did not carry. If any exist, draft the next version of the coding brief — the complete document with changes marked in the study's versioning style, again by editing the original in place — and deliver it as a file alongside the case-status update. If none exist, state plainly: "No brief changes from this document," give the reasoning, and ask the researcher whether they want a version produced anyway; do not simply skip. The default is to draft the next version; the only way not to is the stated verdict plus the researcher's confirmation. Never leave the question unaddressed; an unstated brief check is indistinguishable from a forgotten one. (Identical versions differing only in the header are why the verdict exists: the study's version marks should each mean that something was decided.)
5. **The skill check.** Separately from the brief, ask whether anything learned is study-independent (tool behaviour, a method step, a failure mode) and belongs in this skill rather than in the brief; if so, say what and propose it. Decisions of one study never go in the skill.
6. **The project backup.** Last, once the researcher has the documents: a full ATLAS.ti project bundle, named with the date and the document (for example `2026-11-10 Interview 26 after close-out.atlproj`), saved where the study keeps its backups. If the MCP server offers an export tool, use it; otherwise ask the researcher to export the bundle (File > Export > Project Bundle) and wait. Then check that the file exists and has a plausible size, and record its name and the live quotation count in the case-status entry, so each backup ties to a known state. The document is done only when the backup is confirmed. Never restore or re-import a bundle yourself; that is the researcher's action, and after it the session-start checks run again, because a re-import changes the project instance.

The researcher reviews both files before adopting them — your drafts propose, their acceptance disposes, same as with every quotation. If a session ends early or is interrupted mid-document, deliver an interim case-status update covering what was actually done, flagged as interim, so no session's decisions exist only in a chat transcript — unless the researcher explicitly says not to. The same applies to the brief: an interim session with codebook-level findings gets the verdict-and-confirm step above, not silence.
